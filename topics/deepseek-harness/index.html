Harness 原理

你问「北京现在的天气怎么样？」，模型怎么拿到最新数据？DeepSeek Harness（dsh）是 DeepSeek 开源的智能体运行时，负责把模型、工具和它们交换的信息接起来。[1]

插件怎样给 Agent 添加能力？

拿查天气举例。Cordis 挂载天气插件后，插件把 get_weather 的参数声明和执行函数一起注册到工具服务。组装下一次模型请求时，指定 Agent 可用的工具声明会随请求发给模型。卸载插件会撤销这笔注册。[6][7]

dsh 的架构有哪些设计重点，插件在哪一层？

插件就是 Cordis 运行时的组成单元。启动时，Profile 决定装配哪些插件。运行时，默认 Agent 循环也是一个插件，靠共享服务调用模型、查找工具和访问会话。工具作用域决定 Agent 能看到什么，审批等执行策略通过事件接入。模型用到的历史则从只追加的会话事件中重建。[1][6][8]

    两种讲解视角

    初学者 跟着天气查询理解插件和工具调用 架构师 追踪插件装配、策略边界与会话事件

    从一个天气问题到一条答复

    Harness 是运行模型和工具的程序。工具可以是一个查天气的小程序。模型提出需要查哪个城市，Harness 负责调用小程序，并把查到的数据交回模型。[1]

    查天气的工具从哪儿来？

    启动 dsh 时，Profile 就像一份装配清单，Cordis 按它装好调用模型、查资料等任务所需的部件。比如装上一个天气插件，它会交给 Harness 两样东西。第一样是给模型看的说明，告诉它工具叫什么、需要哪个城市。第二样是实际查询的程序，由 Harness 运行。拿掉这个插件，下一次模型请求里就少了它贡献的那份工具说明。[1][7]

    演示中，挂载时用北京的天气结果回答。卸载后再问同一个问题，模型说明当前无法确认实时天气。这时工具根本没有运行，也就没有结果需要第二次问模型。

    看天气插件如何挂载和卸载 ↑
    1. 让模型知道能查什么你问北京现在的天气。Harness 把问题连同天气工具的用途和必填参数一起发给模型。
    2. 把「请查北京」变成实际查询模型提交天气工具和城市名。Harness 检查这次请求，再执行天气工具。
    3. 把查到的数据变成回答假设工具返回「晴、22°C」，Harness 把结果发回模型。模型读到数据后，组织成一句你能直接读懂的答复。

    为什么同一个问题要问模型两次？

    第一次请模型判断需要什么信息。模型只看到了「查天气」这项工具的说明，还没拿到天气数据。工具运行完以后，Harness 把问题、模型提出的查询和工具给出的数据一起发回去，第二次才有条件根据数据回答。

    如果你同时问北京和上海，模型可以一次提出两笔查询。每笔查询都有自己的编号。演示里北京查到了「晴、22°C」，上海超时，最后的答复就可以给出北京的数据，并说明上海暂时查不到。[4]

    工具超时，或者根本用不到工具

    天气查询超时时，演示中的模型会说明暂时无法确认。像「摄氏度怎样换算成华氏度」这样的问题，模型可以直接用公式回答。此时通常一次调用模型就够了。

    按现象定位设计边界
    现象先查什么为什么分在这层
    模型请求里没有天气工具装配清单、工具注册、当前 Agent 的可见范围配置可替换插件，替换后仍需满足服务契约。
    模型提出调用，工具未运行tool/call 的编号、参数和执行前决策工具可见性与执行授权独立，策略可单独更新。
    两城只查到一城按编号比对两笔 tool/result成功和失败各自回填，重试和副作用补偿由工具与集成方案处理。
    有结果，答复没用到下一次模型请求里的消息历史日志用来重建模型历史，实时流用于界面展示。
    展开装配优先级与插件契约

    web、headless、sdk 和 acp 共享 dsh-base，各自叠加入口组合包。sdk-minimal 使用自己的完整配置。启动时依次应用组合包、Profile 补丁、Harness home 补丁和命令行 --patch。补丁按条目 ID 插入项或替换整项配置。用 dsh --profile web --dump-config 可查看实际装配的树。[1]

    天气插件声明 inject = ['tools']，等待工具服务就绪，再用 ctx.tools.register() 注册声明和执行函数。卸载时会撤销注册，下一次组装请求就缺少它贡献的工具声明。默认循环本身也是插件，替换循环或模型适配器时仍须满足服务接口的取消、流式响应等约定。[1][6][7]

    展开完整回合与消息投影

    Turn（回合）覆盖一次任务处理，可推进多个 Step（步骤）。正常路径的每步包含一次模型请求，可带一批工具调用。ctx.systemPrompt 提供系统提示和工具声明，循环结合消息历史组装请求，再交给 ctx.llm 的适配器发送。下面用成功的北京天气查询展示简化轨迹。[1]

    turn/start
  step/start → 模型请求 → assistant/message
    tool/call → 检查并执行 → tool/result
  step/end
  step/start → 带工具结果再次请求模型 → assistant/message
  step/end
  agent/turn-stopping
turn/end

    如果工具结果还需要模型处理，或有新输入待处理，循环可以再跑一步。准备结束时会经过 agent/turn-stopping 检查。以下事件名来自 dsh，字段和值为教学简写。[1][3]

    会话记录
  user/message       “北京现在的天气怎么样？”
  assistant/message  请求 get_weather，编号 weather_1
  tool/call          weather_1，参数 city=北京
  tool/result        weather_1，结果 晴、22°C

第二次请求的消息历史
  user       北京现在的天气怎么样？
  assistant  工具调用 weather_1，get_weather(city=北京)
  tool       对应 weather_1，晴、22°C

    ctx.sessions 保留只追加的会话事件。deriveMessages() 投影模型所见的历史，适配器再按提供方协议发送。界面可从 agent/assistant-stream 先显示增量文字，完成并提交的 assistant/message 才进入模型历史。失败的 assistant/attempt 留在日志中供排查。[1][3]

    展开工具策略、超时与部分失败

    循环把原始调用批次交给 ctx.tools.execute()。执行器按 Agent 作用域查找工具、核对参数，在 tools/pre-execute 处理审批、拒绝或取消。通过检查后执行函数，tools/execute 可包装超时策略，tools/post-execute 处理结果。策略拒绝时，调用停在函数执行之前。[2][8]

    模型可以在同一条回复提出北京和上海两笔调用。北京成功、上海超时时，下一次请求可以同时携带成功数据和错误信息，每笔结果都对应原编号。演示把超时错误直接回填。实际是否重试取决于执行策略和后续模型请求。[2]
