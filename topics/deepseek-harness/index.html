Harness 原理

你问「北京现在的天气怎么样？」，模型怎么拿到最新数据？DeepSeek Harness（dsh）是 DeepSeek 开源的智能体运行时，负责把模型、工具和它们交换的信息接起来。[1]

    两种讲解视角

    初学者 跟着天气查询理解工具调用 架构师 追踪组件边界、事件与失败处理

    从一个天气问题到一条答复

    Harness 是运行模型和工具的程序。工具可以是一个查天气的小程序。模型提出需要查哪个城市，Harness 负责调用小程序，并把查到的数据交回模型。[1]

    1. 让模型知道能查什么你问北京现在的天气。Harness 把问题连同天气工具的用途和必填参数一起发给模型。
    2. 把「请查北京」变成实际查询模型提交天气工具和城市名。Harness 检查这次请求，再执行天气工具。
    3. 把查到的数据变成回答假设工具返回「晴、22°C」，Harness 把结果发回模型。模型读到数据后，组织成一句你能直接读懂的答复。

    为什么同一个问题要问模型两次？

    第一次请模型判断需要什么信息。模型只看到了「查天气」这项工具的说明，还没拿到天气数据。工具运行完以后，Harness 把问题、模型提出的查询和工具给出的数据一起发回去，第二次才有条件根据数据回答。

    如果你同时问北京和上海，模型可以一次提出两笔查询。每笔查询都有自己的编号。演示里北京查到了「晴、22°C」，上海超时，最后的答复就可以给出北京的数据，并说明上海暂时查不到。[4]

    工具超时，或者根本用不到工具

    天气查询超时时，演示中的模型会说明暂时无法确认。像「摄氏度怎样换算成华氏度」这样的问题，模型可以直接用公式回答。此时通常一次调用模型就够了。

    组件如何协作，状态在哪里流转

    以下以 dsh 的默认 agent-loop 为范围。Turn（回合）覆盖一次任务处理，可以推进多个 Step（步骤）。正常路径中的每个步骤都包含一次模型请求，模型也可以在这次请求中提出一批工具调用。示例假设模型支持工具调用，天气工具已在当前作用域注册。[1]

    回看架构图 ↑

    core/agent-loop

    请求组装与模型适配

    循环用系统提示、会话投影和可用工具的声明组装模型请求。ctx.llm 上注册的适配器负责与选定的模型提供方通信，将返回内容交给循环处理。[1]

    core/tools

    作用域内的工具执行

    循环把原始调用批次交给 ctx.tools.execute()。执行器按智能体的作用域选择工具，处理参数、执行前决策与执行后的结果。调用标识贯穿 tool/call 和 tool/result。[2]

    core/session

    会话事件与消息投影

    循环将消息、调用和结果追加到会话日志，再从日志推导下一次请求的消息历史。流式回复的增量可供实时界面使用，完成的消息与失败尝试按各自的事件写入日志。[3][1]

    天气查询的事件轨迹

    这是一个工具成功、模型在第二次请求后完成回合的简化轨迹。[1]

    turn/start
  step/start → 模型请求 → assistant/message
    tool/call → 查天气 → tool/result
  step/end
  step/start → 带工具结果再次请求模型 → assistant/message
  step/end
turn/end

    从会话事件到第二次模型请求

    会话日志既记录运行过程，也提供模型消息的来源。下图用北京查询展示两种表示。事件名来自 dsh 文档，字段和值是教学简写。[1][3]

    会话记录
  user/message       “北京现在的天气怎么样？”
  assistant/message  请求 get_weather，编号 weather_1
  tool/call          weather_1，参数 city=北京
  tool/result        weather_1，结果 晴、22°C

第二次请求的消息历史
  user       北京现在的天气怎么样？
  assistant  工具调用 weather_1，get_weather(city=北京)
  tool       对应 weather_1，晴、22°C

    循环通过 deriveMessages() 从日志推导消息历史，模型适配器再按提供方协议发送。step/start、step/end 等事件用于运行过程。界面可以用实时流增量先呈现文字，失败尝试可记录为 assistant/attempt，它留在日志内供排查。[1][3]

    失败分支与设计取舍

    工具定义在哪一层生效
    组装请求时向模型提供工具名称、用途和参数结构。执行时还要由作用域内的执行器处理真实调用。tools/pre-execute 可以接入审批、拒绝或取消，再由 tools/execute 包装超时等执行策略，最后由 tools/post-execute 处理结果。[2]
    工具失败如何传递
    以两城查询为例，模型的同一条回复可以包含两个调用。结果仍按编号匹配。北京成功、上海超时时，下一次请求可以同时携带北京的数据和上海的错误信息。工具失败后是否重试，需要看执行策略和后续模型请求。对超时的调用，演示选择把错误直接回填。[2]
    回合何时结束
    如果结果需要模型继续处理，或有新的待处理输入，循环可以再跑一步。准备结束时还会经过 agent/turn-stopping 检查。[1]
    可替换的部件带来什么约束
    Cordis 允许通过插件注册模型适配器、工具、日志和循环。对集成者而言，替换组件时仍需对齐工具可见范围、结果格式与日志语义。会话可从日志重建消息历史，外部工具副作用的重试与补偿需要由工具和集成方案处理。[1][3]

    排查时先看停在哪一步

    看不到查询请求，先检查工具声明是否进入模型请求。已经有 tool/call，就按同一编号跟到 tool/result，看执行、超时或拒绝情况。结果正常但回复没有用到数据时，继续核对下一步实际发送的消息历史和最后生成的回复。[1][2]
