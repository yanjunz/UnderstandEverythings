Pi 怎样知道该用哪条测试命令？

Pi 是一个能在终端里操作代码库的编程助手。你可以只问怎么运行测试。假设这是一个用 npm 的项目，测试命令就可能写在项目的 package.json 文件里。

  1. 模型选择要看的文件。Pi 把问题和可用工具的说明交给模型。模型知道有一个叫 read 的读文件工具，于是回复一个工具名和文件路径。
  2. Pi 在本地读取文件。假设工具读到 "test": "vitest run"。Pi 把这段项目配置作为工具结果，连同原问题交给模型。这就是第二轮比第一轮多出的证据。
  3. 模型根据结果回答。现在它可以解释，运行 npm test 会调用 vitest run。这次只读了配置。要知道测试是否通过，还得实际执行命令并查看退出状态。

如果文件缺失，工具返回读取错误。模型可以再查 README 或向你确认项目目录。在演示里，它选择说明目前缺少哪条证据。工具调用示例 · 读取工具实现

换成 Jest 要改哪里？

如果项目把测试脚本改成 jest，同一个读取工具就会带回新的命令。Pi 可以原样使用这个循环。作者选择读写文件和执行命令等通用工具，一个理由是模型已经熟悉这些操作。作者的设计说明

一次提问，为什么会调用两次模型？

以“这个项目怎么跑测试？”为例。假设当前目录是一个 npm 项目，启用了 read，模型选择先查看 package.json。图中只追踪读取测试脚本的一条路径。

这条路径有两份不同用途的状态。运行时在内存中维护当前消息，供下一轮推理使用。启用持久化时，编码应用的 AgentSession 将相关记录交给 SessionManager 保存，关闭终端后仍可恢复会话。执行循环 · 会话实现

读到脚本toolResult 带回文件正文。假设 scripts.test 是 vitest run。模型可说明运行 npm test 会调用 Vitest。要知道测试能否通过，还需要实际执行。
文件不存在read 执行失败，运行时生成带 isError 的工具结果。下一轮模型能根据错误再查目录、询问项目位置，或说明缺少依据。
模型服务报错若第一次模型请求返回 stopReason = error，本轮产生的是助手错误消息。运行时结束本次循环，尚未分派读取。排查应从模型请求入手，是否重试由上层处理。
追踪请求、工具结果和终端事件

模型接收工具的名称、说明和参数结构。它返回的 toolCall 带调用 ID、名称和参数。运行时按名称找到实际工具，把调用 ID 写入 toolResult.toolCallId。这样即使一次请求读了两个文件，也能把每个结果配回相应的调用。工具调用事件 · 读取工具

tool_execution_end 告知终端一次执行已结束，适合刷新界面。进入下一次模型请求的是结果消息。应用内部的消息还可以包含界面信息，convertToLlm 在请求边界将它们转换为模型可接收的消息。消息转换 · 模型接口

小核心的收益与代价，怎样决定改哪一层？

Mario Zechner 希望能控制每一轮送给模型的上下文。编码应用默认启用 read、bash、edit、write，项目可以用扩展注册自己的工具或响应会话事件。运行时只需按共同的工具接口接收请求、执行、回传结果。默认工具 · 扩展接口 · 作者的设计说明

设计取舍（本页分析）　假设代码库搬到远程工作区，现有 read 可以替换底层文件操作，继续接受相同的路径参数。模型接口和执行循环便能复用。相应地，远程路径怎么解析、连接中断怎样报告，都由工具实现承担。即便工具成功，最终答案仍依赖模型正确解读返回内容。读取工具的操作接口
