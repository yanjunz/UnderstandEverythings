pstack Skill 原理

关掉通知，点了保存，刷新页面却又变成开启。一个编码 Agent 收到这条报告后，该先改代码，还是先复现？pstack 把这类决定写成一套可按需加载的工作流程。它原本是 Lauren Tan 的 Cursor 技能栈，本文分析 Michael Denyer 维护的多宿主移植版。[1]

同一个设置页，三种任务怎么走

切换任务，看模型什么时候加载完整流程、什么时候直接处理，以及显式要求 TDD（测试驱动开发）时会加载哪个 Skill。选「原因未知的故障」还可以比较三种验收证据。

教学模拟。路由依据会话指令，修复和复测依据 Bug fix Playbook 或 TDD Skill。设置页、观测值和根因均为示例。[2][4][7]

两种讲解视角

初学者一次修复为什么需要一张清单 架构师路由、流程组合与执行边界

把「修一下」变成一项能验收的工作

pstack 是一套给编码 Agent 读的 Skill，也就是做某类工作的说明。会话开始时，钩子把选择规则交给模型。只改设置页标题，可以直接改。像通知设置这种原因未知的故障，模型会加载 poteto-mode，使用 Bug fix Playbook，也就是事先写好的修复步骤。用户明确说「先写一个失败的回归测试再修」，则直接加载写回归测试用的 tdd Skill。[2][3]

  1. 先看到问题。 关掉通知，保存，刷新。刷新前显示「关」、刷新后显示「开」，这才是要修的现象。
  2. 沿着证据找原因。 示例里，点击保存后记录仍是「开」。提前写入「关」的测试记录后，刷新却能正确显示「关」。由此把修复范围缩小到保存动作。
  3. 用原来的方式再试一次。 再做一遍「关掉、保存、刷新」。刷新后仍然是「关」，才能确认用户遇到的现象消失。[4]

为什么要登记步骤？

一项工作可能做到一半才发现某步不适用。pstack 要求把该步留在清单并写明跳过原因。回看时，你能知道哪些检查确实做过、哪些只有理由。[3]

工作流由 Markdown 描述，由宿主工具执行

以 Claude Code 插件为例。pstack 提供路由指令与流程约定，宿主提供会话、工具和权限，模型负责选路，主 Agent 根据实际证据验收。[2][3]

验收与合并就绪。 原界面仍复现就回到定位，只有单测通过就继续在原界面验收。改动执行安全或数据完整性约束的代码时，复测通过后仍须独立正确性审查，才能标记为可合并。[3][4][7]

注入规则、加载 Skill 与保存待办

hooks/hooks.json 在启动、恢复、清空或压缩会话时调用 session-start.sh。启用时，脚本返回 session-start-context.md 的路由文本。模型将原因未知、多文件、设计取舍和性能问题等任务交给 poteto-mode。如用户明确要求 tdd，会直接加载该 Skill。[2]

poteto-mode/SKILL.md 先选 playbooks/bug-fix.md 或 feature.md 等流程，把步骤放入宿主待办。可用的 Claude Code 工具包括 TaskCreate 和 TaskUpdate，或已配置的 TodoWrite。没有待办工具时会使用未提交的 Markdown 清单，照录步骤并标记 skip: <reason>。[3]

模型按判断加载 principle-*，例如 principle-prove-it-works。项目 Playbook 可用 extends 扩展内置步骤，check-playbooks.mjs 会验证扩展引用的步骤是否仍存在。[3][6]

Bug fix Playbook 的完整步骤
  1. 在原界面复现。 主 Agent 操作关闭通知、保存、刷新，确认通知重新开启。
  2. 排除候选原因。 在示例里，保存后直接读记录仍是开启，准备一条已关闭的记录后，刷新能显示关闭。这把调查范围缩小到保存路径。
  3. 规划并委派修复。 主 Agent 界定任务，将 worker.md 路径传给 pstack:poteto-agent，审查回传的 diff。跨函数边界时通常先运行 architect。涉及接口、所有权、数据语义等变化的修复必须先过该步骤。
  4. 重复原界面操作。 保存后刷新仍是关闭，才有原故障路径通过的证据。只测保存函数，仍需查界面有没有用到结果、刷新能否读到新值。
  5. 整理可验证的提交。 有低成本的回归测试路径时，验证同一用例修复前按预期失败、修复后通过。把失败用例的提交排在修复之前。成本高或路径不明时采用可行的复现检查，并说明取舍。
  6. 进入 Opening a PR Playbook。 记录故障、根因、修复和验证依据。执行安全或数据完整性约束的代码有改动时，还要等独立审查。主 Agent 的自审与 CI 无法代替这项审查。

步骤按上游 Playbook 概括，设置页与观测值是教学示例。[3][4][5][7]

宿主移植、设计取舍与源码

各移植版共享 plugins/pstack/skills/。Markdown 以 Claude Code 的工具词汇为主，各宿主提供映射。在 Codex，Agent 的委派动作映射为 spawn_agent，插件钩子需受信任才运行。在 DeepSeek Harness，skills-only 装法提供共享技能及配套脚本等文件。用户显式请求 poteto-mode，委派使用宿主暴露的 subagent 等工具。[8][9][10]

移植仓库同步 Cursor 上游时先应用机械转换，再保留 tools/forks.json 明示的工具适配或流程差异。共享的技能正文可以维护在一处，各宿主的工具差异由映射处理。[8]

设计取舍。 按需加载降低一项任务需要读取的规则量，使流程可复用。路由和执行仍依赖模型遵守指令，跨宿主时尤其要核对工具和权限。脚本可检查步骤引用，实际故障是否修复则由运行证据判定。[3][6]

读者问题

pstack Skill 的原理是什么？
把做事方法写成可组合的技能文件，由 poteto-mode 选择 Playbook。主 Agent 把步骤登记成待办，按需调用子技能、子 Agent 和宿主工具，最后用实际产物验证结果。[3][4]
装了 Skill，流程就一定会执行吗？
自动路由取决于宿主集成和钩子状态。启用的会话钩子提供提示，选择和执行仍由模型与宿主完成。skills-only 安装可显式调用，实际能否委派或操作界面取决于宿主开放的能力。[8][10]
