grill-me Skill 原理

「给读书会做一个报名页。」如果名额满了，要开放候补吗？只有先知道这个答案，才值得讨论怎么补位。Matt Pocock 的 /grill-me 把这样的依赖整理成设计树，按轮推进，直到你和 Agent 对方案达成共识。[1][2]

读书会报名要不要开放候补？

扮演活动组织者，回答这一轮的设计问题。再让模拟仓库返回事实，看看哪些问题会被解锁，哪些分支会被跳过。

问题依赖

  • 是否开放候补
  • 是否发送提醒
  • 提醒时间 ← 发送提醒
  • 补位方式 ← 开放候补＋仓库事实
  • 补位保留多久 ← 自动补位

模拟仓库调查

教学模拟。人工作答推动轮次，侧栏按钮仅模拟工具返回；现场问题由模型判断，演示用固定依赖来展示机制。范围限于候补和提醒。[2]

两种讲解视角

初学者跟着一次报名决策理解追问顺序 架构师分析 Skill 边界、依赖和停止条件

先问会改变后续的问题

/grill-me 是做设计访谈的 Skill。你只要说出想做什么，Agent 就会把可能影响方案的选择列出来。它给建议，由你决定。如果你说「满额即关闭」，后面就跳过怎么补位和给候补者保留多久。[4]

  1. 先问能独立回答的。「要候补吗？」和「要提醒已经报名成功的人吗？」互不影响，可以一轮问完。当前所有能问的问题合称前沿。
  2. 先查现有能力。你同意候补。Agent 去查仓库有没有后台任务能力，回来后才有依据建议自动或手动补位。提醒提前多久可以先定。
  3. 按答案打开下一层。你选自动补位，才出现「给下一位候补者保留多久？」选手动则略过示例里的自动保留时限。
  4. 最后核对共识。没有待答问题、相关调查也到齐时，核对双方理解是否一致。Agent 等你确认后才可据此行动。[2]

哪些问题适合留到原型？

例如候补页面应该怎样排版，光描述可能选不出来。作者文档建议先做可丢弃的原型，用实际体验产生新事实，再回到访谈作决定。[4]

把问答看成逐轮解依赖

上游由入口和可复用访谈规则组成。入口 grill-me/SKILL.md 用 disable-model-invocation: true 标明用户触发，并要求通过 Skill 工具加载 grilling。只装入口时，共用访谈 Skill 仍需由宿主发现和加载。[1][3]

前沿由已确认的前置条件决定
一轮收集所有当前适用且依赖已满足的决定。若补位方式仍未选，保留多久就属于后续轮次，即使「开放候补」已经确定。上游叫它设计树。读书会示例的补位方式同时依赖一个用户决定和一个工具事实，架构上可把它理解为带条件的依赖关系。[2]
查询事实和作决定是两条路径
上游要求在新的上下文中派子 Agent 调查环境。例如查能否运行后台任务。没有调查结果时，只有补位方式和下游受阻；提醒时间还在前沿。查到后台执行能力缺失，结论是「自动化需要额外开发」，是否扩大本期范围仍由用户决定。[2]
建议的措辞让决定可确认、可反驳
每个问题有编号、题目和建议。源码规定把问句写成回答「是」就接受建议的形式，例如缺少后台任务时问「本期由组织者手动补位吗？」。用户仍可以选择新增自动化。回答更新假设；发现一项决定依赖了错误前提时，应重新打开受影响的分支。[2][3]
暂时问不了与已结束需要区分
调查未完成时，可能暂时没有能问的问题，但相关分支仍未解决。分支全部处理后才进入共识确认。确认属于提示词规定的行为，宿主和模型的能力会影响执行效果。作者文档指出，前沿由模型判断，有时会漏掉题目间的依赖。[2][3]

落盘由哪个 Skill 负责？

grill-me 的共享理解留在对话中。需要把领域词汇和架构决定留给项目后续使用时，grill-with-docs 会同时调用 grilling 和 domain-modeling，维护 GLOSSARY.md 和 ADR（架构决策记录）。[4][6]

读者问题

grill-me 的原理是什么？
按依赖组织设计访谈。Agent 把可以查证的事实交给工具调查，把可决定的问题按轮交给用户，收到答案后再重算下一轮。[2]
为什么有的版本一次只问一题？
早期 grill-me 正文明确要求一次问一题。本文固定的上游版本已把访谈抽到 grilling，按前沿成轮提问。相依问题依旧分轮。作者文档仍给出了在 CLAUDE.md 中声明逐题偏好的方式。[5][3]
