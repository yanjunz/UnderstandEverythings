Magpie 的运行原理

为什么 Claude Code 可以使用 DeepSeek？跟着一次请求，看看本地网关怎样选择模型、转换协议并返回结果。

观看核心动画 ↓ 读者问题
>_
magpie
✦

先记住这一句：Magpie 是运行在你电脑上的模型网关：接住 Agent 的请求，找到合适的模型，必要时翻译双方的 API 格式，再把回复送回来。

初学者 · 从问题到回答

          

            
各方在请求中做什么

            

              把这件事想成去一家有翻译服务的餐厅。你向服务员点菜，翻译协调口味和语言，真正做菜的还是厨师。
            

            

              

                >_
                
Agent · 干活的助手

                

                  例如 Claude
                  Code、Codex。它组织对话、读取项目，并在获得授权后执行工具。
                

                
就像服务员：接任务，安排事情。

              

              

                ⇄
                
Magpie · 中间的桥

                

                  管理接入配置，决定请求发给谁，并协调 API 格式、账号和回复。
                

                
就像翻译兼调度员：把双方接起来。

              

              

                ✦
                
模型 · 思考的引擎

                

                  例如
                  DeepSeek、Kimi。根据收到的上下文，生成文字或提出工具调用。
                

                
就像厨师：真正产出这道菜。

              

            

            

              所以你可以保留熟悉的 Agent
              操作方式，把背后的模型换掉。能否完整工作，仍取决于模型能力和协议兼容性。
            

            

              第一次见这些术语？打开小词典 ＋
              

                

                  
API / 协议

                  

                    程序之间约定的沟通方式：请求发到哪里、字段叫什么、回复长什么样。
                  

                

                

                  
Provider / 服务商

                  

                    提供模型服务的入口，包含地址、认证方式和模型列表；它也可以是本地模型服务。
                  

                

                

                  
Base URL

                  

                    API 的基础地址，像收件地址。改向 Magpie 后，Agent
                    就先来找它。
                  

                

                

                  
流式输出

                  

                    回复生成一点就传一点，因此你不必等全部写完才看到内容。
                  

                

                

                  
Token

                  

                    在「消耗多少 token」里，它是模型处理文字的计量单位；在「认证
                    token」里，它指访问凭据。二者不是同一回事。

              请求流程小结
              

                Agent 负责组织和行动。
模型负责生成。
Magpie 负责把它们接起来。
              

              改配置接入 → 路由选去处 → 按需转换 → 返回回复
            

          

        


        

          
架构师 · 本地网关的接口与状态

          

            
沿着一次调用划分职责

            

              以 Claude Code 经 Magpie 调用 DeepSeek 为例。Agent 按 Anthropic
              Messages 的接口发送「解释一下这个函数」，目标模型通过 Chat
              Completions 提供服务。这个案例采用普通模型 API 路径。路由实现
            

            

              

                
接入配置

                

                  internal/agent 按 Agent
                  的配置格式设置入口地址、认证和模型，并记录原设置以供断开时恢复。这个阶段建立本地入口指向。Agent wiring
                  · 配置和认证实例
                

              

              

                
请求路由

                

                  网关根据请求的模型或路由组，从已配置的服务商、账号和模型中选出候选。会话亲和性可以让连续请求留在已有账号上。Gateway routing
                

              

              

                
协议适配

                

                  跨协议时，入口解析为 Request 和
                  Part，再按上游协议构造请求。回程将流式事件重新编码回 Agent
                  的协议。中间表示源码
                

              

            

            

              
跟着字段走一次

              
    
                
  1. 
                  入口读取请求。 Claude Code 向本机的
                  /v1/messages 发送
                  model: deepseek/deepseek-chat、用户消息和输出上限。入口路径决定如何解析字段，调用方身份可以另行归因。入口与调用方
                
    2. 
                
  2. 
                  路由确定下一跳。
                  网关从供应商配置取目标协议、基础地址和认证方式。假设 DeepSeek
                  上游只提供 Chat Completions，转发请求的
                  model 对应上游的
                  deepseek-chat，消息与输出上限也按目标 API
                  编码。候选选择 ·
                  字段表示
                
    3. 
                
  3. 
                  回程保留关联。
                  比如模型流式返回工具名称和分段参数，转回 Messages
                  时需要把这些分片放回同一次工具调用，并保留调用标识。普通模型
                  API 路径中，Agent 收到这条工具请求后才决定是否执行。流式事件
                  · 执行边界
                
    4. 
                
  4. 
                  失败点决定是否可换上游。
                  如果上游在任何回复发给 Agent
                  前返回可重试错误，网关可以尝试下一位候选。已经发出部分回复时，客户端已有流式状态，需要按该路径的失败行为处理。Routing
                  记录可以用来核对实际候选和响应方。失败分支
                
    5. 
              

            

            

              设计取舍。共用中间表示可以让各协议共用路由与转发逻辑。集成时仍要验证工具调用标识、结束信号和目标模型的能力。故障切换也取决于客户端是否已经收到回复，开始输出后需要保留已发送内容的语义。故障行为
              · 协议表示
            

          


          

            
请求和流式回复如何转换

            

              不同 API 对同一个问题，用的字段名和事件格式不一样。Magpie
              在需要跨协议时，先读成共同的内部结构，再写成对方能理解的格式。
            

            

              

                协议翻译台精简字段示意 · 非完整请求
              

              

                
              

              

                

                  

                    

                      01 / AGENT 发出Messages
                    

                    POST /v1/messages
                    

                  

                  

                    

                      02 / 共同内部结构IR
                    

                    
先理解含义，再重新包装

                    
角色user

                    
内容类型text

                    

                      内容解释一下这个函数
                    

                    这是概念图，不是实际 JSON
                  

                  

                    

                      03 / 服务商收到Chat
                    

                    POST /chat/completions
                    

                  

                

                

              

            

            

              

                为什么不能只改模型名字？因为请求字段、工具调用、推理内容和流式事件都可能不同。回复也需要反向转换，Agent
                才能继续读取。
              

              

                每次都翻译吗？不一定。双方 API
                兼容、条件允许时，可以走原生转发路径；跨协议转换也无法补出目标模型本来没有的能力。
              

            

            

              ≋
              

                
流式回复也要边收边翻译

                

                  服务端发来一小段 → 解码为内部事件 → 编码成 Agent 的事件格式 →
                  立即向下传递。工具调用的名称、参数和结束信号同样需要正确对齐。

额度耗尽时如何切换

            

              你可以把多个模型放进一个「路由组」，让 Agent
              只选这个组。下面用最容易理解的
              order
              模式实验：按顺序尝试，前一个不能回答才找下一个。
            

            

              

                ⑂ group /
                  daily-codingorder · 顺序优先
              

              

                

                  状态和耗时均为教学示意。
                

                

                  

                    01
                    

                      DeepSeek 主账号第一顺位
                    

                    待命
                  

                  

                    02
                    

                      Kimi 备用模型第二顺位
                    

                    待命
                  

                  

                    准备好了。试着发送一次请求。
                  

                

              

            

            

              

                切换有前提。需要存在可用候选，且失败适合重试。只有一个账号、没有后备时，错误仍会返回
                Agent。
              

              

                中途不能随意接力。这个实验模拟的是回复尚未对客户端输出时的失败；已经输出部分回复，不能当作从未发生过，直接拼上另一个模型的答案。
              

            

            

              除了顺序，还有哪些路由思路？ ＋
              

                

                  
smart

                  

                    在还有额度的订阅里，优先选择更快重置的，减少额度浪费。
                  

                

                

                  
rotate / usage

                  
分别是每轮轮换成员，以及优先选择用量较少的成员。

                

                

                  
会话亲和性

                  

                    为保留上下文缓存，连续对话可能留在已有账号上；真实选择还要综合账号状态和组设置。
                  

                

              

            

          


          

            

              
普通 API、订阅桥接与隐私边界

            

            

              

                A
                
执行工具，通常还是 Agent 的工作

                

                  模型可以返回「调用 read_file」的结构化请求。Magpie 把它转成
                  Agent 理解的格式，由 Agent
                  检查权限并执行，再把结果带到下一轮。
                

                

                  模型提出调用→Agent 执行→结果进入下一轮
                

                

                  这是普通模型 API 路径。Magpie 另有
                  MCP、内置工具和订阅桥接等功能，不能把所有路径都等同于这一条。
                

              

              

                B
                
订阅接入，不全是直接转发 HTTP

                

                  API key 服务商、本地模型和订阅账号的接入方式不同。例如 Claude
                  订阅路径会驱动本地真正的 claude 程序，并通过 MCP
                  桥接工具。
                

                

                  MCP 是连接工具与 AI
                  应用的一种协议。理解主干后，再研究具体订阅的认证与进程管理，会更容易。
                

              

            

            

              ◇
              

                

                  「本地网关」意味着请求先经过本机，不等于全部在本地推理。
                

                

                  选择云端模型时，请求仍会离开电脑。Magpie
                  有可选的隐私脱敏功能，默认关闭；开启后会尝试把识别到的敏感值换成占位符，回复时再还原。它不是「任何信息都不会外传」的保证。
                

              

            

          

        


        

          
读者问题

          

            

              Magpie 怎么改 Codex、Claude Code 的
              Gateway？原网关地址和凭据从哪里来？
            

            

              这里改的是 Agent 用来发模型请求的基础地址。 Agent
              已支持自定义服务入口，Magpie
              为它填入一个新的地址和对应的入口凭据。新请求由 Agent 主动发到
              Magpie。原来的网关继续在原地址运行，Magpie
              的接入逻辑还会记录改过的设置，以便断开时恢复。Agent 接入实现
            

            

              

                
Codex 改哪里

                

                  以选择 Magpie 自定义 provider 的接法为例，Codex 配置中的
                  [model_providers.magpie] 使用
                  base_url = "http://127.0.0.1:3425/v1"、wire_api = "responses"
                  和发给 Magpie 的 Bearer token。启用该 provider
                  后，模型请求发到本机的 /v1/responses。Codex 配置源码
                

              

              

                
Claude Code 改哪里

                

                  普通网关接入会设置 settings.json 的
                  env.ANTHROPIC_BASE_URL 为
                  http://127.0.0.1:3425，并配置面向 Magpie 的
                  ANTHROPIC_AUTH_TOKEN。Claude Code 继续使用
                  Messages 协议，向新地址发
                  /v1/messages。接入是否生效还取决于实际生效的配置，企业托管配置可有更高优先级。Claude Code 配置源码
                  · 接入文档
                

              

              

                
原来的网关在哪里

                

                  如果 Agent 原本已有自定义地址，支持该 Agent
                  的适配器可以读取它写在配置里的地址。Magpie
                  自己要连接的上游则来自供应商预设、手工添加的 Base
                  URL，或受支持账号的接入逻辑。对一个此前未知的私有
                  Gateway，需要知道它的地址、协议和可用凭据，再按兼容接口接入。配置读写
                  · 供应商设置
                

              

            

            
改地址之前
  Agent ── 原服务的凭据 ──→ 原服务

改地址之后
  Agent ── Magpie 入口的凭据或本机访问策略 ──→ Magpie
  Magpie ── 所选上游的 API key 或已授权账号 ──→ 上游服务

            

              换地址以后，上游仍然鉴权。 Magpie
              的本机入口按自己的访问策略接收调用，跨机器共享时要按共享配置提供
              Gateway key。Magpie
              发往上游时，使用该供应商配置的凭据，举例来说可以是 Bearer API
              key，也可以是 Anthropic 接口使用的
              x-api-key。受支持的订阅使用已登录的账号和相应接入逻辑，比如 Codex 的
              ChatGPT 登录账号，或通过本地 claude 进程接通的 Claude
              订阅。能连上本机入口，只说明第一段链路通了。入口鉴权
              · 上游鉴权 ·
              订阅桥接
            

            

              如果你开发的是云端 Agent，127.0.0.1 指 Agent
              服务实际运行的机器。浏览器界面在用户电脑上，也不会改变后端发请求的位置。此时
              Agent 的配置要使用它能访问的 Magpie 地址，以及相应的入口凭据。
            

          

          

            

              Magpie 怎么知道 Agent 用哪家模型？我的 Agent 和自建 LLM Gateway
              能接入吗？
            

            

              如果你的 Gateway 提供 Magpie 支持的模型
                API，它就可以作为自定义上游。
              你的 Agent 可以同时作为调用方，向 Magpie 发请求。Magpie
              需要接到这次请求，才能根据其中的模型名选择供应商。只要 Agent
              仍直连原 Gateway，调用就沿原路径走。自定义供应商
              · 请求路由
            

            

              假设你的 Gateway 支持 OpenAI Chat Completions，并提供模型
              team-chat。以下地址和名称是示意。
            

            
你的 Agent → Magpie → 自建 LLM Gateway → 实际模型

Agent Base URL  http://127.0.0.1:3425/v1
Agent model     my-gateway/team-chat

Magpie 自定义供应商  my-gateway
上游 Base URL        https://gateway.example.com/v1
上游模型             team-chat

            
    
              
  1. 
                在 Magpie 添加自定义供应商，配置 Gateway 的 Base
                URL、协议、认证和模型。Chat Completions 是一种选择，Magpie
                还支持 Responses、Anthropic Messages 和 Gemini 等接口。Agent
                使用 Magpie 入口的凭据，上游凭据则配在对应供应商。供应商协议与凭据
              
    2. 
              
  2. 
                把自研 Agent 的模型请求地址改为 Magpie，并选择 Magpie
                列出的模型标识。推荐使用配置后的
                供应商/模型 名，或选择已配置的路由组。图中的
                my-gateway 是假定的供应商 ID，实际填写时以 Magpie
                显示的为准。模型标识与路由组
              
    3. 
              
  3. 
                Magpie 可从已知 Agent 的路径、调用凭据或
                User-Agent 识别谁发来了请求。对自研
                Agent，可以直接配置客户端的模型 API 地址。Agent
                在列表里是否有专用的一键接入，与这次模型请求能否转发是两个问题。调用方识别源码
                · Agent 接入配置
              
    4. 
            

            

              如果你想把整个 Agent 当作上游，需要由它本身或适配层提供兼容的模型接口。比如你的 Agent
              只接受「提交任务」并返回任务 ID，Magpie
              需要一个能按模型协议接收消息、返回回复的适配层才能调用它。若客户端需要流式输出和工具调用，适配层也要遵循相应协议。上游接口
              · 消息与流式事件
            

            

              排查时看两边的路由记录。Magpie 的
              X-Magpie-Provider、X-Magpie-Model
              能确认它选了哪一跳。若自建 Gateway
              还会二次路由，最终用哪家模型要看自建 Gateway 的记录。响应方记录
