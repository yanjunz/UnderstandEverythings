Magpie 的运行原理

为什么 Claude Code 可以使用 DeepSeek？跟着一次请求，看看本地网关怎样选择模型、转换协议并返回结果。

观看核心动画 ↓ 架构师速览 读者问题

先记住这一句：Magpie 是运行在你电脑上的模型网关：接住 Agent 的请求，找到合适的模型，必要时翻译双方的 API 格式，再把回复送回来。

研究对象 yetone/magpie ↗3 个互动实验 · 3 道自测题

改了哪个地址？两段请求各用什么凭据？

看 Claude Code、Codex 或自研 Agent 怎样改模型入口，再跟着请求到上游。 切换鉴权场景可以看到 401 由哪一方返回，以及请求有没有离开 Magpie。

保留 ChatGPT 登录的成功路径适用于本机回环。要演示远程共享成功，请选 Codex 自定义 provider，由它发送共享 Gateway key。

初学者 · 从问题到回答

          

            
各方在请求中做什么

            

              把这件事想成去一家有翻译服务的餐厅。你向服务员点菜，翻译协调口味和语言，真正做菜的还是厨师。
            

            

              

                >_
                
Agent · 干活的助手

                

                  例如 Claude
                  Code、Codex。它组织对话、读取项目，并在获得授权后执行工具。
                

                
就像服务员：接任务，安排事情。

              

              

                ⇄
                
Magpie · 中间的桥

                

                  管理接入配置，决定请求发给谁，并协调 API 格式、账号和回复。
                

                
就像翻译兼调度员：把双方接起来。

              

              

                ✦
                
模型 · 思考的引擎

                

                  例如
                  DeepSeek、Kimi。根据收到的上下文，生成文字或提出工具调用。
                

                
就像厨师：真正产出这道菜。

              

            

            

              所以你可以保留熟悉的 Agent
              操作方式，把背后的模型换掉。能否完整工作，仍取决于模型能力和协议兼容性。
            

            

              第一次见这些术语？打开小词典 ＋
              

                

                  
API / 协议

                  

                    程序之间约定的沟通方式：请求发到哪里、字段叫什么、回复长什么样。
                  

                

                

                  
Provider / 服务商

                  

                    提供模型服务的入口，包含地址、认证方式和模型列表；它也可以是本地模型服务。
                  

                

                

                  
Base URL

                  

                    API 的基础地址，像收件地址。改向 Magpie 后，Agent
                    就先来找它。
                  

                

                

                  
流式输出

                  

                    回复生成一点就传一点，因此你不必等全部写完才看到内容。
                  

                

                

                  
Token

                  

                    在「消耗多少 token」里，它是模型处理文字的计量单位；在「认证
                    token」里，它指访问凭据。二者不是同一回事。

控制面 · 接入前配置

数据面 · 请求状态

              按拒绝位置排查
              
                
现象请求走到哪先核对

              
              
                

                  Magpie 入口 401
                  远程共享入口拒绝，未尝试任何上游。
                  Agent 发给 Magpie 的 Gateway key。
                

                

                  上游 401
                  入口通过，已联系目标服务。单一候选时失败回给 Agent。
                  选中供应商的 API key 或登录账号。
                

                

                  上游 429
                  回复未发出、错误可重试且有备用候选时，可尝试下一位。
                  路由记录里的候选、额度和限额。
                

                

                  流已开始后失败
                  客户端已有部分回复。
                  已发出的事件和结束状态。另一路模型的结果不能直接拼接。

普通 API、订阅桥接与隐私边界

            

            

              

                
普通模型 API

                
模型提出工具调用 → Magpie 转换并返回 → Agent 检查权限、执行并发起下一轮。

              

              

                
Claude 订阅

                
Magpie 驱动本地 claude 进程，沿用订阅账号，由 MCP 桥接工具调用。订阅桥接实现

              

            

            
数据去向 走云端上游时请求会出本机。本地脱敏是可选功能，默认关闭。

            

              设计取舍与能力边界
              
    
                
  • 统一 IR 让多协议共用路由逻辑。代价是适配层要正确映射调用 ID、参数和事件，结果仍受目标模型能力限制。
    • 
                
  • 账号亲和性有利于缓存复用，故障切换则要兼顾账号状态和客户端已经看到的结果。
    • 
                
  • Claude 订阅桥接要管理进程和会话，Magpie 的内置工具也有自己的路径。普通 API 的分工适用于上面示例。
    • 
                
  • 脱敏开启时，用占位符替换识别到的内容，回复时还原。保护范围取决于识别覆盖。实现与边界对照

读者问题

          

            

              Magpie 怎么改 Codex、Claude Code 的
              Gateway？原网关地址和凭据从哪里来？
            

            

              这里改的是 Agent 用来发模型请求的基础地址。
              Claude Code 的普通接法和 Codex 的自定义 provider 接法会把对应地址指向 Magpie，并配置入口 token。
              Codex 在本机保留 ChatGPT 登录的接法改的是顶层 openai_base_url，
              仍沿用现有登录凭据。接入后，Agent 主动向 Magpie 发请求。
              原服务仍可在原地址访问，Magpie 会记录接入设置供断开时恢复。Agent 接入实现
            

            

              

                
Codex 改哪里

                

                  自定义接法选择 model_provider = "magpie"。
                  Codex 配置中的
                  [model_providers.magpie] 使用
                  base_url = "http://127.0.0.1:3425/v1"、wire_api = "responses"
                  和发给 Magpie 的 Bearer token，模型请求发到
                  /v1/responses。本机保留 ChatGPT 登录的接法仍用内建
                  OpenAI provider，只把顶层 openai_base_url 指向
                  http://127.0.0.1:3425/backend-api/codex。
                  选 Codex 原有模型时可按原路径往 ChatGPT 转发。选择 Magpie 列出的模型时，
                  由 Magpie 按自己的供应商配置发出上游请求。Codex 配置源码
                

              

              

                
Claude Code 改哪里

                

                  普通网关接入会设置 settings.json 的
                  env.ANTHROPIC_BASE_URL 为
                  http://127.0.0.1:3425，并配置面向 Magpie 的
                  ANTHROPIC_AUTH_TOKEN。Claude Code 继续使用
                  Messages 协议，向新地址发
                  /v1/messages。接入是否生效还取决于实际生效的配置，企业托管配置可有更高优先级。Claude Code 配置源码
                  · 接入文档
                

              

              

                
原来的网关在哪里

                

                  如果 Agent 原本已有自定义地址，支持该 Agent
                  的适配器可以读取它写在配置里的地址。Magpie
                  自己要连接的上游则来自供应商预设、手工添加的 Base
                  URL，或受支持账号的接入逻辑。对一个此前未知的私有
                  Gateway，需要知道它的地址、协议和可用凭据，再按兼容接口接入。配置读写
                  · 供应商设置
                

              

            

            
改地址之前
  Agent ── 原服务的凭据 ──→ 原服务

改地址之后
  Agent ── 本机回环规则 / 远程共享 Gateway key ──→ Magpie
  Magpie ── 所选上游的 API key 或已授权账号 ──→ 上游服务

            

              两段各有自己的访问规则。普通本机回环请求无需共享密钥。
              magpie 是客户端可填写的普通 token。
              跨机器共享需要启用共享并提供有效的 Gateway key。已能连接远程共享入口时，
              错钥匙会在发往上游之前被拒绝。Magpie 发往上游时，使用该供应商配置的凭据，
              举例来说可以是 Bearer API
              key，也可以是 Anthropic 接口使用的
              x-api-key。受支持的订阅使用已登录的账号和相应接入逻辑，比如 Codex 的
              ChatGPT 登录账号，或通过本地 claude 进程接通的 Claude
              订阅。若入口收到了请求，但上游拒绝其 API key，仍会在第二段出现 401。入口鉴权
              · 上游鉴权 ·
              订阅桥接
            

            

              如果你开发的是云端 Agent，127.0.0.1 指 Agent
              服务实际运行的机器。浏览器界面在用户电脑上，也不会改变后端发请求的位置。此时
              Agent 的配置要使用它能访问的 Magpie 地址，以及相应的入口凭据。
            

          

          

            

              Magpie 怎么知道 Agent 用哪家模型？我的 Agent 和自建 LLM Gateway
              能接入吗？
            

            

              如果你的 Gateway 提供 Magpie 支持的模型
                API，它就可以作为自定义上游。
              你的 Agent 可以同时作为调用方，向 Magpie 发请求。Magpie
              需要接到这次请求，才能根据其中的模型名选择供应商。只要 Agent
              仍直连原 Gateway，调用就沿原路径走。自定义供应商
              · 请求路由
            

            

              假设你的 Gateway 支持 OpenAI Chat Completions，并提供模型
              team-chat。以下地址和名称是示意。
            

            
你的 Agent → Magpie → 自建 LLM Gateway → 实际模型

Agent Base URL  http://127.0.0.1:3425/v1
Agent model     my-gateway/team-chat

Magpie 自定义供应商  my-gateway
上游 Base URL        https://gateway.example.com/v1
上游模型             team-chat

            
    
              
  1. 
                在 Magpie 添加自定义供应商，配置 Gateway 的 Base
                URL、协议、认证和模型。Chat Completions 是一种选择，Magpie
                还支持 Responses、Anthropic Messages 和 Gemini 等接口。Agent
                使用 Magpie 入口的凭据，上游凭据则配在对应供应商。供应商协议与凭据
              
    2. 
              
  2. 
                把自研 Agent 的模型请求地址改为 Magpie，并选择 Magpie
                列出的模型标识。推荐使用配置后的
                供应商/模型 名，或选择已配置的路由组。图中的
                my-gateway 是假定的供应商 ID，实际填写时以 Magpie
                显示的为准。模型标识与路由组
              
    3. 
              
  3. 
                Magpie 可从已知 Agent 的路径、调用凭据或
                User-Agent 识别谁发来了请求。对自研
                Agent，可以直接配置客户端的模型 API 地址。Agent
                在列表里是否有专用的一键接入，与这次模型请求能否转发是两个问题。调用方识别源码
                · Agent 接入配置
              
    4. 
            

            

              如果你想把整个 Agent 当作上游，需要由它本身或适配层提供兼容的模型接口。比如你的 Agent
              只接受「提交任务」并返回任务 ID，Magpie
              需要一个能按模型协议接收消息、返回回复的适配层才能调用它。若客户端需要流式输出和工具调用，适配层也要遵循相应协议。上游接口
              · 消息与流式事件
            

            

              排查时看两边的路由记录。Magpie 的
              X-Magpie-Provider、X-Magpie-Model
              能确认它选了哪一跳。若自建 Gateway
              还会二次路由，最终用哪家模型要看自建 Gateway 的记录。响应方记录
